## 官方来源与维护入口澄清（2026-11-06）

用户原话：“从官方下载就是说的 软件官方提供了下载源,但是没提供apt源,这个仓就是 后面要做成收集这些源, 然后 更新上去 按照 ubuntu标准使用方式 ,如果有版本变动,那么 也有一键升级 校对 各个 软件源的一致性信息的脚本. 已达到  ubuntu apt upgrade 升级要求的规则遵循.”

首批 Go 与 RustDesk 的目标不变，来源适配须同时满足官方原包获取与标准 APT 安装、升级。不能以当前代码只适配 GitHub `.deb` 为由缩窄用户目标，也不能从“官方提供下载”推导出用户允许本项目托管转换后的安装包。

维护侧提供一条命令，复用现有发行版发现、同步、隔离验证和渲染脚本；完整检查通过才产出可发布候选，失败不更改已生效状态。使用侧仍用 `apt update`、`apt install`、`apt upgrade`，不引入常驻升级器，不在安装阶段偷偷联网下载主程序。新版本使用 Debian 版本规则，拒降级、同版本内容替换；无版本变动时继续核对既有信息并续签，不改软件更新时间。

工程现状：RustDesk 原样官方 `.deb` 分流保留。Go 本地构包、ELF 核查及模拟升级只证明生成包自身可用，不证明官方提供了该 `.deb`；当前尚未解决官方 Linux 归档与标准 APT 的格式差异，不能只产出悬空索引或冒充已接入。

## 独立构包与三段式发版（2026-11-09）

出处：同一会话，用户随后明确：“如果是这样你可参考其他仓库 buil.sh+github actions 配合的 直接上传 assets 的三段式 发版-> 构建+上传 -> 删除冗余版本”；“从 其他项目复制来一份 git_tag.sh 比如 /home/ubuntu/workspace/projects/project_template_go 项目里的”；“那就要 gen_deb_golang.sh 这样的独立脚本 在 build.sh 时候关联extend方式调用是吧”。

按此分层适配模板：`gen_deb_golang.sh` 复用已有 Go 构包逻辑，`build.sh` 只做扩展调用和产物汇集，Actions 创建 Release、构建并上传完整 assets、成功后清理冗余。Go 生成 `.deb` 经本仓 Release assets 分发，RustDesk 原样 `.deb` 仍从官方获取；源码、数据分支和 Pages 不存包。包版本取官方版本加 Debian 修订，仓库脚本沿用唯一 `VERSION`。清理保护现行索引引用的 assets，不机械按版本号减二删除。

用户最新还要求：“把准备 密钥的 命令给我放在 REAME.md里面”，并提供丢失／泄露换钥后的使用者报错及修复指令，“达标后 commit+push吧 我根据你给的命令去 生成并放密钥去”。因此本次完成代码、文档和隔离验收后提交推送；生产密钥由用户生成和配置，不代替用户实际发版、上传或删除远端版本。

## 最小实现

1. 软件条目声明官方发布来源、版本通道、架构与资产匹配规则。按上游实际标记选 LTS/稳定版；上游未声明 LTS 时不能自行称为 LTS。不造通用插件框架。
2. 维护标准 APT 索引、包版本、依赖、架构、官方地址、大小和 SHA256；用专用私钥签名元数据，客户端使用 `Signed-By`。
3. 优先使用 APT 内建 `mirror+https`，将索引请求与官方 `.deb` 请求分流；先用真实 APT 验证，不仅凭文档或字符串检查宣布可用。
4. 源码、数据分支和 Pages 不存安装包；官方已有 `.deb` 继续官方直下，Go 等必要转换产物经本仓 Release assets 分发。分别记录原始资产和生成包的摘要、大小与出处。
5. Actions 定时检查官方更新，发布成功后从确切部署状态生成 README 固定区域和静态列表。只保留必要元数据与历史 by-hash，软件更新时间不因单纯续签变化。
6. Actions 只使用一个用户 Secret：`APT_HUB_GPG_PRIVATE_KEY`。公钥和指纹由流程取得并公开，发布者身份使用工作流上下文。
7. `VERSION` 与 `git_tag.sh` 管理维护脚本版本；按模板适配的发版命令由用户主动执行，日常软件版本更新不冒用仓库脚本版本，也不重写已有发布标签。

多官方域名的最小入口布局以协议核对与实测决定；不凭空假定 APT 可以按任意包名选择域名，也不因索引路径问题退回二进制镜像。

## 本轮执行顺序

2026-11-06 用户确认：“那就按这个目标推进到达标才算完工”。目标是 Actions 自动维护、Pages 仅发布签名元数据、安装包从软件官方直下。一般客户端无需 fork；自部署者使用自己的签名身份，不能沿用原维护者的提交身份。当前先修复已定位问题，再完成新版完整链路、独立审查和真实发布验收；生产配置与推送、发版仍按当次授权处理。

同日用户补充：“是 像 add-apt-repository ppa:longsleep/golang-backports 这样的用法吧,最终做出来”。客户端交付应是一条命令完成首次加源，之后使用标准 APT 安装、更新；不要求用户手动追版本，不新增常驻客户端。`ppa:` 是 Launchpad 专用简称，不把 Pages 源冒称为 PPA。

1. 两路 Cursor 并行：一路用隔离 APT 实测索引/官方下载分离，一路独立核对官方手册、源码及多域名边界；均不改生产代码。
2. 小哈复核原始证据，固定最小数据与命令契约，再按文件所有权让 Cursor 修改同步、模板和工作流。保留正确的官方资产校验、签名、Ubuntu 支持核对等能力，替换错误的包存储路径。
3. 串行集成、独立审查、实际复测。旧镜像方案通过记录不能代替新版验收。
4. 文档去除旧镜像描述与多余配置，验收闭环后用户身份提交推送并读取远端确认。

## 验收

- 真实 APT 验签更新、下载安装包；请求日志证明签名索引来自 Pages，RustDesk 包来自官方，Go 生成包来自确切 Release assets，而非假下载或安装时联网脚本。
- Pages 与 `apt-data` 产物不含 `.deb`；生成包作为 Release assets，不以 Git 单文件大小限制软件包。
- 对齐 Ubuntu 当前标准支持期与官方架构，声明组合均能解析精确包版本依赖；不把 ESM 或 GUI/硬件兼容性混作已验证。
- 篡改摘要、错误签名、上游资产变更、网络失败、并发与重复运行有明确结果；失败不发布错误状态，不回退无签名或第三方包。
- README 与网页只展示成功发布状态，区域外正文保持；生产配置未完成时不能宣称公网源已上线。
- 本地、远端 CI 与独立审查分别核实；原 CI 的 ShellCheck 失败仍需处理，不以架构调整掩盖。

## 非破坏性约束

不改本机系统源、全局 keyring、dpkg 数据、Git/SSH、shell 或 OpenClash；不安装目标软件，不执行其维护脚本。生产私钥只由用户配置在 Actions 中，所有验证临时文件只放项目 `tmp/`。不重写已推送历史。
