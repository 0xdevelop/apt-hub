# apt-hub 项目规范

本文档汇总本项目已确认的开发与发布约定。后续协作必须遵守本文；禁止以口头习惯或临时便利替代这些条款。

## 1. 仓库位置

- 必须将 `apt-hub` 放在与 `project_template_go` 等其他项目同级的目录，路径为 `/home/certa/workspace/apt-hub`。
- 禁止另建位置存放本仓库。
- 已有该路径的本地仓库时，必须直接复用，禁止重复克隆。

## 2. 克隆方式

- 必须统一使用 SSH 克隆和远程传输，地址为 `git@github.com:0xdevelop/apt-hub.git`。
- 禁止使用 HTTPS 作为 Git 远程地址。
- 现有 `origin` 若不是上述 SSH 地址，必须改为 SSH 后再拉取或推送。

## 3. 版本号

- 禁止手写版本号。
- 仓库版本必须由 `git_tag.sh` 管理。
- 软件包版本必须以官方最新 LTS 为准，并由脚本跟随官方版本，禁止在脚本或配置中写死软件包版本。

## 4. 构建与发版解耦

- 本地可以单独运行构建和测试，不必因此触发发版。
- 真正发版时，必须先由 `git_tag.sh` 打 tag，再由 GitHub Actions 在同一条链路中联动完成构包和上传。
- 禁止拆开这条 tag 联动的构包与上传链路。
- 禁止让普通代码推送单独发布资产。

## 5. 自动升版逻辑

- Actions 可以调用 `git_tag.sh` 自动升版，这与发版约定不冲突。
- 必须遵守“有实质变化才升、没变化不升”。
- 禁止为了升而升。
- 必要性必须由现有发布计划判断，例如上游 Go 更新或构包输入变化才进位。
- 空 Release 必须只补包，禁止因此新打 tag 或盲目升版。

## 6. 发布清理脚本

- 禁止在清理逻辑中手写版本号，例如 `v0.0.0`、`v0.0.1`。
- 必须按 tag 递减确定清理下限。
- 不足两代时必须跳过清理，禁止强行删除。
- 沿原三段式，`Release` 与 `Build`（含 Pages 部署及 README 回写）成功后自动调用现有清理；前序失败不清理，有效索引引用的资产受保护。

## 7. 测试夹具

- 禁止写死会与产品版本碰撞的具体版本号，例如 `v0.0.9`。
- 夹具使用的版本必须与当前产品版本不冲突，且不得随产品版本升迁而再次撞车。
- 禁止通过放松来源校验来掩盖夹具版本冲突。

## 8. 发版授权

- 未经用户明确授权，禁止 `push`，禁止触发发版。
- 普通 `push` 虽不会立即发版，但会影响每天北京时间 12:17 的定时发布；`push` 前必须先征得授权。
- 可以在本地提交；在获得授权前，必须将改动保留在本地。

## 9. 公网 Pages

- 排查操作本身不改公网 Pages、不手工删除旧 Release。
- 已授权的正常发布/自动维护按原链联动 Pages 与受索引引用保护的两代清理；不能把排查期限制扩大为永久关闭清理。

## 10. Hermes 相关改动

- 复查 Hermes 改动时，必须重点检查是否写死版本号，以及是否把构建和发版错误地绑在一起。
- 发现局限后，必须做最小本地修正并完成验证。
- 禁止在复查或修正过程中擅自发版。
- 复制源脚本方面已经完善的能力必须沿用，禁止无故改坏。
